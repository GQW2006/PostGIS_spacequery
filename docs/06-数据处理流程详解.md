# 〇、先看全景

```
① 数据获取          高德 API / Overture / GHSL / DataV
        ↓
② 坐标系统一        GCJ-02 → WGS-84（不做这一步偏 400 米）
        ↓
③ 入库与校验        字段标准化、几何检查、范围检查
        ↓
④ 建索引            GiST（空间）+ B-tree（属性）
        ↓
⑤ 路网拓扑清洗      制图几何 → 路由图（顶点 + 边 + 成本）
        ↓
⑥ 服务发布          GeoServer 发布 WMS / WFS
        ↓
⑦ 终检              一页指标确认无回退
```

**核心认知**：①②③④ 是做"数据"，⑤ 是做"图模型"，⑥ 是做"服务"。
这三件事性质完全不同，混在一起做一定乱。

# 一、坐标系：中国数据的第一道坎

## 1.1 问题

中国的地图数据有两套坐标：

| 坐标系 | 谁在用 | 特点 |
| --- | --- | --- |
| **WGS-84** | GPS、OpenStreetMap、国际数据 | 真实地理坐标 |
| **GCJ-02（火星坐标）** | 高德、腾讯、DataV、Google 中国 | 在 WGS-84 上做了非线性偏移 |

国家规定公开地图必须用 GCJ-02。所以**高德/DataV 的数据是 GCJ-02**，
而 OSM/Overture 是 WGS-84。直接叠加，整体错开 **300–500 米**。

## 1.2 怎么发现

不是靠"看"出来的，而是靠**数值验证**：

1. 取 DataV 的区县边界，取 Overture 的路网
2. 沿边界采样几百个顶点，算每个点到路网边界的最近距离
3. 平均约 224 米——但不是均匀偏移，说明不是单纯制图简化
4. 做**平移搜索**：尝试各种 (dx, dy) 平移，看能否显著降低平均距离
5. 结果：平移 (−0.0025°, +0.0025°) 后，平均距离从 224.7 米降到 64.1 米，**改善 71.5%**

**结论**：存在系统性基准偏移，不是随机误差。

## 1.3 怎么修

实现标准的 GCJ-02 → WGS-84 反算（[`data_pipeline/geo_utils.py`](../data_pipeline/geo_utils.py)）：

- 正向：WGS-84 → GCJ-02 是公开的解析公式
- 反向：没有解析解，用**迭代逼近**——反复用正向公式修正，直到误差 < 1e-10

在成都该变换给出的偏移量是 **(+0.00250, −0.00243)**，
与实测最优平移 (−0.0025, +0.0025) 完全吻合，互相印证。

**入库前对每个顶点都做这个变换**，之后所有数据统一在 WGS-84。

> 记忆点：**能不能发现坐标系偏移，是 GIS 专业和业余的分水岭。**
> 绝大多数个人项目栽在这里而自己不知道。

# 二、入库与校验

## 2.1 校验清单

跑 [`sql/01_validate_data.sql`](../data_pipeline/sql/01_validate_data.sql)，检查 8 项：

| # | 检查项 | 方法 | 本次结果 |
| --- | --- | --- | --- |
| 1 | 行数 | `count(*)` | 边界 1 / 区县 20 / 路网 202,077 / POI 3,036 |
| 2 | 坐标系 | `ST_SRID(geom)` | 全部 4326 ✅ |
| 3 | 几何有效性 | `ST_IsValid` | 无效 0 ✅ |
| 4 | 空几何 | `ST_IsEmpty` | 0 ✅ |
| 5 | 几何类型 | `ST_GeometryType` | 与预期一致 ✅ |
| 6 | 空间范围 | `ST_Extent` | 都在成都范围内 ✅ |
| 7 | 落界 | `ST_Contains(市域, poi)` | 越界 0 条 ✅ |
| 8 | 重复点 | 同名且 < 50m | 1 组（可忽略） |

## 2.2 为什么这些检查必须有

- **几何无效**：`ST_IsValid` 为 false 的几何会让 `ST_Intersects` 等函数报错或给错结果
- **落界检查**：POI 越界说明裁剪时坐标系用错了（很常见）
- **重复点**：会让统计数量虚高

## 2.3 幂等性

所有 SQL 脚本都必须**可重复执行**。做法：

- 建表用 `DROP TABLE IF EXISTS ... CASCADE` + `CREATE TABLE`
- 建索引用 `CREATE INDEX IF NOT EXISTS`
- 加列用 `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`

否则第二次跑就会报错，无法复现。

# 三、建索引

## 3.1 空间索引为什么必须

没有 GiST 索引时，`ST_Intersects(geom, 视口)` 要对 20 万行逐行算几何关系，
**慢两个数量级**。有索引则会先用包围盒快速过滤。

## 3.2 建了什么

跑 [`sql/06_indexes.sql`](../data_pipeline/sql/06_indexes.sql)：

| 表 | 索引 | 类型 | 用途 |
| --- | --- | --- | --- |
| `chengdu_poi` | `geom` | GiST | 视口查询、附近检索 |
| `chengdu_poi` | `category` | B-tree | 按类型筛选 |
| `chengdu_poi` | `(category) INCLUDE (name,district)` | B-tree | 覆盖索引，避免回表 |
| `chengdu_poi` | `name` | B-tree（pattern_ops） | 前缀搜索 |
| `chengdu_roads` | `geom` | GiST（8.4 MB） | 视口查询 |
| `chengdu_roads_routing` | `geom` | GiST（49 MB） | 路由几何 |
| `chengdu_roads_routing` | `source` / `target` | B-tree | **pgRouting 找邻接边靠它** |
| `chengdu_roads_routing_vertices_pgr` | `the_geom` | GiST | 起点吸附 |

## 3.3 一个工程细节：清理重复索引

早期脚本用 `xxx_gix` 命名，新脚本用 `xxx_geom_gix`，导致同一列上出现两个 GiST 索引。
这是纯浪费（写放大 + 占空间），所以脚本开头先 `DROP INDEX IF EXISTS` 旧名。

> 记忆点：**索引不是越多越好。同一列两个同类型索引是 bug，不是保险。**

# 四、路网拓扑清洗（重点）

## 4.1 概念：为什么"路网"不能直接用来算路径

Overture 给的 202,077 条路段是**制图几何**：一段段独立的线，画在地图上好看，
但它不是一个"图（Graph）"。

路由算法要的是：

```
图 = 顶点集合 + 边集合 + 通行成本
     ↑节点编号     ↑边连接哪两个节点   ↑走这条路要多久
```

而原始数据里：

- ❌ 没有顶点编号
- ❌ 没有说"这条边的两端是第几号节点"
- ❌ 没有通行时间
- ⚠️ 路口处两条线可能只是"看起来相交"，实际端点坐标差几米

**拓扑清洗就是把这些补齐。**

## 4.2 拓扑构建的原理（三步）

```
① 提取所有线段的端点
   每条边贡献 2 个点 → 202,077 × 2 = 404,154 个点

② 把空间上重合的端点归并为同一个顶点
   用容差聚类：5 米内的端点视为同一个路口
   否则同一个十字路口的 4 条边会有 4 个不同端点，永远连不上

③ 给顶点编号，把每条边的 source/target 指回去
```

本次结果：

| 指标 | 数值 |
| --- | --- |
| 端点总数 | 404,154 |
| 聚类后顶点数 | 168,677 |
| 被合并的交叉口 | 104,906 个 |
| 平均每顶点合并 | 2.40 个端点 |

## 4.3 我们实际怎么做的（SQL 实现）

跑了 [`sql/02_routing_topology.sql`](../data_pipeline/sql/02_routing_topology.sql)。

> **重要背景**：本机 pgRouting 4.0.1 **没有 `pgr_createTopology` 函数**
> （该函数属于 `topology.sql`，这个构建没装）。所以改用 PostGIS 手工实现，
> 效果等价，而且每一步都看得见。

关键三步的 SQL 思路：

**① 提取端点**

```sql
-- 每条边取起点和终点，拼成一张端点表
SELECT id AS edge_id, 'S' AS which, ST_StartPoint(geom) FROM chengdu_roads
UNION ALL
SELECT id, 'E', ST_EndPoint(geom) FROM chengdu_roads
```

**② 空间聚类（核心）**

```sql
-- ST_ClusterDBSCAN 把 5 米内的点归为一簇
-- 注意：先投影到 EPSG:32648（UTM 48N）再用米做容差
-- 直接用度数会因为经纬不等长产生偏差
ST_ClusterDBSCAN(ST_Transform(pt, 32648), eps := 5.0, minpoints := 1) OVER ()
```

**③ 生成顶点表并回填**

```sql
-- 顶点坐标取簇内质心（比取某一点更能代表路口中心）
SELECT row_number() OVER (ORDER BY cluster_id) AS id,
       ST_Centroid(ST_Collect(geom)) AS the_geom
FROM endpoints GROUP BY cluster_id;

-- 回填
UPDATE chengdu_roads_routing e SET source = v.id
FROM endpoints ep JOIN vertices v ON v.cluster_id = ep.cluster_id
WHERE ep.edge_id = e.id AND ep.which = 'S';
```

## 4.4 QGIS 等效操作步骤（手动做法）

如果你要在 QGIS 里亲手做一遍，或者面试时被问"你平时怎么处理拓扑"，按这个流程：

### 准备

1. 打开 QGIS → 左侧「浏览器」面板 → 展开 **PostgreSQL** → 新建连接
   - 主机 `127.0.0.1`，端口 `5432`，数据库 `gisdb`，用户名 `postgres`，密码 `<DB_PASSWORD>`
2. 双击 `public` → 双击 `chengdu_roads` 图层，加载到地图
3. 确认右下角坐标显示为 4326（度），不是投影坐标

### 第一步：打断相交线

**目的**：让所有交叉处真正断开成节点。

1. 菜单 **处理 → 工具箱**（Ctrl+Alt+T）
2. 搜索 `v.clean` → 打开 **GRASS → 矢量 → v.clean（清理拓扑）**
3. 参数设置：
   - 输入图层：`chengdu_roads`
   - 清理工具：勾选 **break**（在交叉处打断）
   - 容差：`0.00005`（度）
4. 运行，得到新的 `cleaned` 图层
5. 如果 GRASS 不可用，用原生工具：**处理工具箱 → 矢量几何 → 按线打断（Split with lines）**，
   用图层自身作为切割线

### 第二步：检查悬挂点

**目的**：找出"应该连但没连"的端点。

1. 处理工具箱搜索 **拓扑检查器（Topology Checker）**
2. 「矢量 → 拓扑检查器」→ 配置
3. 添加规则，图层选 `cleaned`：
   - **must not have dangles**（不能有悬挂端点）
4. 点击「验证全部」
5. 地图上会标出所有悬挂点——这些是断头路或没接上的路口

### 第三步：吸附修复

1. 菜单 **矢量 → 吸附** 或按 `Shift+S` 打开吸附工具栏
2. 开启吸附，模式选 **顶点**，容差 `5.00000 米`
3. 开启 **拓扑编辑**（避免移动时产生新缝隙）
4. 对新出现的错误悬挂点，手动拖动端点吸附到最近线上
5. 改完再跑一次拓扑检查器

### 第四步：写回数据库

**目的**：让 QGIS 里的成果回到 PostGIS，供 pgRouting 使用。

1. 右键图层 → **导出 → 要素另存为**
2. 格式：**PostgreSQL SQL dump** 或直接选 **PostgreSQL** 数据库连接
3. 表名填 `chengdu_roads_routing`，勾选「覆盖已存在的表」
4. 坐标系 `EPSG:4326`

### 第五步：用 SQL 补 source/target

QGIS 本身不做顶点编号，这一步还是要在数据库里做：

1. QGIS 菜单 **数据库 → DB 管理器** → 打开 SQL 窗口，连到 gisdb
2. 粘贴 `sql/02_routing_topology.sql` 的第 2–4 步（提取端点 → 聚类 → 回填）
3. 执行

> **为什么推荐用 SQL 而不是纯 GUI**：
> 20 万条边手动修拓扑不现实；SQL 可重复、可版本管理、结果可验证。
> GUI 适合**理解概念**和**抽查修复**，不适合全量处理。

## 4.6 成本设定

| 参数 | 取值 | 依据 |
| --- | --- | --- |
| 步行速度 | 1.2 m/s（4.32 km/h） | 常用经验值 |
| `cost` | `length_m / 1.2` | 单位：秒 |
| `reverse_cost` | 同 `cost` | 步行双向 |
| 不可步行 | `-1` | pgRouting 视为不可通行 |

不可步行类：`motorway`（高速）、`standard_gauge`（铁路）、`subway`、`tram`、
`monorail`、`light_rail`、`narrow_gauge`、`unknown`。

**为什么保留 `trunk`**：中国 trunk 通常是快速路/国道，大多有辅道或人行道。
若一并禁行，主干网络会大面积断裂，连通率显著下降。

## 5.5 ⚠ 必踩的坑：WMS 1.3.0 的 bbox 顺序

这是 GeoServer 最高频的"图是空白"原因。

| 版本 | EPSG:4326 的 bbox 顺序 |
| --- | --- |
| **WMS 1.1.1** | `minx,miny,maxx,maxy`（经度在前）✅ |
| **WMS 1.3.0** | `miny,minx,maxy,maxx`（**纬度在前**）⚠️ |

WMS 1.3.0 遵循 CRS 定义的轴序，而 EPSG:4326 官方轴序是「纬度,经度」。
所以传 `bbox=103.9,30.55,104.2,30.78` 会被理解成纬度 103.9°（不存在），渲染空白。

**两个解法**：① 用 `version=1.1.1`；② 用 1.3.0 时把 bbox 改成 `30.55,103.9,30.78,104.2`。

> 这个坑我们**实际踩过一次**——第一次 WMS 出图是纯白，原因就是这个。

# 八、这套流程能讲什么（面试素材）

| 环节 | 可讲的点 |
| --- | --- |
| 坐标系 | 用平移搜索**量化验证**基准偏移，而不是靠肉眼 |
| 数据获取 | 不信第三方 `count`，用实际返回条数做判据 |
| 拓扑清洗 | 制图几何 ≠ 路由图，容差是核心参数 |
| 连通性诊断 | 先看总指标会误判，**归因后才能下结论**（70% → 99.65%） |
| 索引 | 同一列两个同类型索引是 bug；GiST 是空间查询的命门 |
| 服务发布 | WMS 1.3.0 bbox 轴序坑 |
| 工程规范 | 所有脚本幂等可重跑、终检脚本防回退 |
